一次下游 IoT 故障如何拖垮 data-router：MQTT 重连风暴事故复盘

Posted by jamie Blog on 2026-08-11 · 阅读 -- 次

MQTT 重连风暴与 Native Thread OOM 的完整复盘

项目 内容
事故时间 2026 年 8 月 10 日晚
影响范围 生产与测试环境设备连接
直接表现 设备离线、data-router 容器停止
最终原因 重复重连导致本地线程资源耗尽

摘要

data-router 负责维护设备连接，并将设备数据推送到下游 IoT 平台。正常情况下，设备只需建立一次 MQTT 连接并长期保持，因此原有重连机制中的并发缺陷长期没有暴露。

2026 年 8 月 10 日晚，下游 IoT 平台出现异常，生产和测试环境均无法正常建立连接。持续性的连接失败触发了 data-router 原有重连机制中的竞态：SDK 自动重连、业务主动重连和设备重复初始化相互叠加，底层 MQTT 客户端及线程不断累积。最终 JVM 无法创建新的本地线程，抛出：

1

java.lang.OutOfMemoryError: unable to create new native thread

随后 data-router 服务进程退出。

核心结论：

下游 IoT 平台故障是事故诱因；data-router 缺少重连单飞、并发上限、连接超时和完整资源清理，才是故障扩散为自身宕机的直接原因。

本次整改并不试图保证下游永远可用，而是保证：即使下游长时间不可用，data-router 也只能以受控方式重连，不能因为重试而拖垮自身。

事故时间线

以下时间线根据服务日志和匿名化微信群故障反馈记录整理。原始截图中的群名、昵称和内部系统画面不在本文展示。

时间 阶段 现场情况
8 月 10 日 21 点后 连接异常出现 生产和测试环境陆续无法连接下游 IoT 平台，已有 MQTT 连接开始断开。
22 点后 重连持续放大 日志集中出现 Connection lost、EOFException 和 Connect already in progress，服务内部线程持续增长。
服务停止 容器退出 JVM 抛出 unable to create new native thread，data-router 进程退出，运行中的容器列表中已看不到该服务。
8 月 11 日 09:02 群内发现 群内反馈全部设备离线，并确认下游 IoT 侧也存在离线现象，开始核对影响范围。
09:14 确认范围 部分设备恢复，部分仍离线；现场确认生产和测试环境均受到影响，并询问下游平台是否有变更。
09:18 重启恢复 重启 data-router 后重新建立部分设备连接，服务恢复对外工作。
09:21 以后 进入排查 初步判断大量并发重连拖垮服务；随后通过历史日志确认 Native Thread OOM，并开始代码级整改。

重启后能够恢复，说明设备数据和基础配置并未永久损坏；真正的问题集中在进程内部的连接状态、重连任务和线程资源。

日志证据与故障链路

事故日志呈现出一条连续而完整的证据链。单独看每一类异常都可能只是普通网络波动，组合起来则清楚地指向重连失控。

1. MQTT 连接丢失

1
2

org.eclipse.paho.client.mqttv3.MqttException: Connection lost
Caused by: java.io.EOFException

EOFException 表示客户端读取网络数据时，对端连接已经关闭。可能原因包括 Broker 异常、网络中断、对端重启或心跳超时。

这类错误应当触发受控重连，本身不应造成服务宕机。

2. 同一客户端发生重复连接

1

Connect already in progress (32110)

该错误证明一个连接操作尚未结束时，又有其他线程对同一个 Paho 客户端发起连接。SDK 自动重连与业务回调主动重连叠加，是形成这一现象的重要条件。

3. JVM 无法创建本地线程

1
2

java.lang.OutOfMemoryError:
unable to create new native thread

该异常不等同于 Java Heap 已满。每个 Java 线程都需要操作系统分配线程栈、PID 和本地内存。当 MQTT 客户端及其线程持续累积，容器的内存或线程数量限制最终会被耗尽。

完整故障链路

1
2
3
4
5
6
7
8

下游 IoT 平台不可用
    -> MQTT Connection lost
    -> SDK 自动重连 + 业务主动重连
    -> 同一设备重复创建或连接 MQTT 客户端
    -> 旧客户端和线程池未及时清理
    -> 本地线程资源耗尽
    -> OutOfMemoryError
    -> data-router 进程退出

原有机制为何没有拦住重复创建

原有代码并非完全没有考虑重复创建。它使用 Redisson 分布式锁控制同一 deviceId 的初始化，并用 Map 保存已经创建的 IoTDevice。

设计意图接近“同一设备只创建一次”，但在异常连接场景下仍存在多个缺口。

问题一：锁租期短于连接耗时

锁租期约为 5 秒，而下游异常时 MQTT 连接可能持续几十秒。锁提前过期后，前一个连接仍在执行，后一个线程已经可以再次创建设备。

1
2
3
4
5

线程 A 获得锁并开始连接
-> 5 秒后锁自动过期
-> 线程 A 仍在连接
-> 线程 B 再次获得锁
-> 同一个 deviceId 开始第二次连接

问题二：Map 操作不是原子的

containsKey()、创建设备和 put() 是三个独立步骤。原来的 HashMap 也不是线程安全容器，多个线程可能同时判断设备不存在并各自创建连接。

最终 Map 中可能只保留一个实例，但另一个 MQTT 客户端及其线程已经被创建。

问题三：两套重连机制相互竞争

华为 IoT SDK 内部自动重连与业务 connectionLost 回调主动重连同时存在，两条重连路径绕过了统一的并发控制。

1
2
3

SDK 正在重连
+ 业务回调再次调用 connect
= Connect already in progress

问题四：失效客户端没有被完整清理

失效连接只做上层关闭时，底层 Paho 客户端、接收线程和 SDK 线程池可能没有及时终止。每次重连都会进一步累积资源。

根因结论

这次事故可以分为三个层次：

层次 结论
事故诱因 下游 IoT 平台持续不可用，生产和测试环境连接同时断开。
机制缺陷 data-router 的设备初始化和重连缺少原子控制、并发上限、超时退出及完整资源清理。
直接死因 重复连接持续创建 MQTT 相关线程，最终触发 unable to create new native thread。

因此，不能简单地把事故归因于下游平台故障。

更准确的说法是：

下游 IoT 平台故障触发了 data-router 重连机制中的并发和资源管理缺陷，最终形成级联故障。

整改方案

整改原则是把重连从“收到异常就再次 connect”改造成一个有唯一入口、有并发边界、有超时、有退避、可取消、可清理的完整生命周期。

1. 关闭 SDK 自动重连，统一重连入口

通过 CustomOptions 关闭 SDK 内部自动重连，所有重连任务统一交给 data-router 的 DeviceReconnectCoordinator，避免 SDK 与业务代码相互竞争。

1
2

CustomOptions options = new CustomOptions();
options.setReConnect(false);

2. 按 deviceId 原子创建和发布设备

新增设备实例注册表。同一个 deviceId 同时只允许一个线程执行创建，其他调用者等待并共享同一次创建结果。

设备必须完成参数设置、监听器注册和连接后，才会发布给其他线程使用。

这种重复调用抑制机制通常称为 Singleflight：

1
2
3

10 个线程同时请求 device-001
-> 只有 1 个线程真正创建 IoTDevice
-> 其他 9 个线程等待并共享结果

device-002 仍然可以独立处理，因此它不是全局单例，而是按 Key 合并重复调用。

3. 固定重连工作线程数量

全服务共享一个固定大小的重连调度器，工作线程数量限制为 2。

大量设备同时离线时，只会形成受控任务队列，不会为每个断线事件创建新线程。

4. 同一设备的连接生命周期串行化

初始化、重连、主动关闭和关闭后重新初始化都按照 deviceId 进入同一个连接槽。

同一个设备不能并发连接，不同设备仍可并行处理。

5. 失败退避与永久错误识别

连接失败后采用逐步退避：

1

1s -> 2s -> 4s -> 8s -> 16s -> 30s

最大等待时间为 30 秒。鉴权失败等永久错误不再持续重试，而是清理连接并记录失败状态。

6. 连接看门狗

每次连接设置 75 秒看门狗。

连接长时间没有返回时，主动关闭对应的底层 Paho 客户端。如果看门狗已经关闭，则直接拒绝新连接，避免连接在没有超时保护的情况下执行。

7. 完整清理底层资源

关闭设备时依次处理：

  • 关闭华为 IoT SDK 客户端；
  • 强制断开并关闭底层 Paho MQTT 客户端；
  • 停止 SDK 内部线程池；
  • 取消当前设备的重连任务；
  • 按具体实例精确移除注册信息，避免旧回调误删新连接。

8. 安全停机

Spring 开始停止 data-router 后，服务先进入 shuttingDown 状态，拒绝新设备初始化，然后取消重连、终止活动连接、清理客户端和线程池。

1
2
3
4
5
6

收到停止信号
    -> 拒绝新设备初始化
    -> 取消重连任务
    -> 中断活动连接并清理 MQTT 客户端
    -> 停止共享线程池
    -> JVM 退出

停机过程设置最大等待期限，防止某个无法退出的 SDK 调用长期阻塞容器关闭。

设计边界

当前部署只有一个 data-router 实例，因此采用 JVM 内按 deviceId 协调即可，不再依赖短租期的 Redis 分布式锁。

如果未来扩展为多实例，需要重新设计跨实例的设备归属和连接协调机制。

验证结果

整改完成后，围绕事故中出现的竞态、超时、OOM 和停机问题补充了针对性回归测试。

验证项 结果
data-router 单元及并发测试 60 项全部通过
九模块 Maven 打包 BUILD SUCCESS
同设备并发初始化 只创建一个 IoTDevice
重复 connectionLost 只保留一个重连任务
连接超时 看门狗清理 Paho 客户端
关闭与重新初始化竞态 旧实例不会影响新实例
停机期间的新初始化 立即拒绝并完成有界清理
模拟 Native Thread OOM 共享调度器受控重试，不扩散线程

修复后的故障表现：

1
2
3
4
5
6

IoT 平台不可用
    -> 每个设备最多保留一个重连任务
    -> 全服务最多两个重连线程执行
    -> 失败后逐步退避
    -> 超时连接被主动清理
    -> data-router 保持存活并等待平台恢复

下游故障期间，设备数据仍可能暂时无法推送，但故障不会再通过无限重连轻易扩散为 data-router 自身宕机。

经验与后续关注

1. 重试是完整的可靠性机制

可靠重试至少要具备：

  • 最大并发数；
  • 超时时间；
  • 失败退避；
  • 重试去重；
  • 任务取消；
  • 永久错误识别；
  • 资源释放；
  • 服务停机处理。

缺少约束的重试，本身就可能成为新的故障源。

2. 外部故障必须被隔离

1
2

正确边界：下游不可用 -> 当前业务失败或延迟 -> 调用方保持存活
错误边界：下游不可用 -> 无限重试 -> 资源耗尽 -> 整条链路停止

这与微服务中的熔断、限流、隔离和降级遵循相同原则：阻止故障沿调用链继续扩散。

3. OOM 不一定是 Java Heap 问题

遇到 unable to create new native thread 时，应优先检查：

  • JVM 当前线程数；
  • 线程池是否被重复创建；
  • -Xss 配置；
  • 容器内存限制；
  • cgroup PID 限制；
  • ulimit -u；
  • MQTT 客户端和线程池是否正确关闭。

盲目增加 -Xmx 可能进一步压缩本地内存空间，使线程创建问题更加严重。

4. 异常场景才真正检验连接管理

“一次连接成功”只能验证正常路径。连接管理还应覆盖：

  • 下游长时间不可用；
  • 网络反复抖动；
  • 大量设备同时断开；
  • 连接过程永久阻塞；
  • 连接期间服务停止。

5. 一个设备一个连接仍需容量规划

本次修复消除了重复连接和线程泄漏，但当前架构仍为每个设备保留一个常驻 MQTT 连接。

设备规模增长后，需要持续关注：

  • MQTT 连接总数；
  • JVM 线程数；
  • Java Heap 和本地内存；
  • 文件描述符数量；
  • 心跳与重连流量；
  • 下游平台的连接上限。

建议监控

建议增加以下监控和告警：

  • JVM 线程总数；
  • 活跃 MQTT 客户端数；
  • 待执行及正在执行的重连任务数；
  • MQTT 连接耗时和超时次数；
  • 容器内存使用量；
  • 文件描述符和 PID 使用量；
  • 容器退出原因与历史日志留存。

结语

这次事故表面上是下游 IoT 平台连接异常，最终表现为全部设备离线和 data-router 服务停止。

深入排查后发现，真正导致服务宕机的是原有重连机制在异常情况下产生了重复连接和线程资源累积，最终触发：

1

OutOfMemoryError: unable to create new native thread

经过整改，data-router 已补齐以下能力：

  • 按设备原子创建连接；
  • 重复重连抑制；
  • 固定线程池隔离；
  • 失败退避；
  • 连接超时保护；
  • MQTT 资源强制清理；
  • 安全停机。

外部依赖发生故障无法完全避免。系统真正需要保证的是：

外部故障不能无限放大，并最终拖垮系统自身。
