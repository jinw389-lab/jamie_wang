同事说MVCC解决了幻读，我打算反驳他

Posted by jamie Blog on 2021-09-06 · 阅读 -- 次

1. 前言

前几天，同事跟我无意中聊到了 MySql 中的 MVCC。同事说在可重复读的情况下，MVCC 可以解决幻读。我一听，感觉不妥，随手丢了一个示例给他，让他跑一遍。这个示例大致是这样的。

发现问题了没有？在第一步中的查询结果和第四步中的查询结果条数不同，多了一条id为3的数据。根据幻读的定义，在同一事务中，后一次查询出来的数据存在前一次没有查询出来的数据。 所以该现象不就是产生了幻读了吗？

2. MVCC 到底能否解决幻读

MVCC能否解决幻读？ 根据上面的例子。一看就知道答案是不能，但是不管是网上还是某些讲 MySql 的书籍上都在说，MVCC解决了幻读。那这到底是咋回事呢？

3. 快照读与当前读

回答上面的问题，我们先来说说两个名词，快照读与当前读，这是MySql中的两种读模式。 平时，我们直接通过 select * from t_user 这种方式，其实就是快照读。

另外一种当前读，是对于会对数据修改的操作( update 、 insert 、 delete )都是采用当前读的模式， 另外一些以下两种也是
1、select * from table where ? lock in share mode; （加共享锁）
2、select * from table where ? for update; （加排它锁）

所以以上第一步骤中，是在快照读的模式下，而第四步中的查询是在当前读的模式下。

综上：MVCC 解决了快照读模式下的幻读，不能解决当前读模式下的幻读。

4. 应该如何解决幻读

上面已经说到 MVCC 不能解决当前读模式下的幻读，那么这个问题在 MySQL 中又是如何去解决呢？

第一张图中，事务 a ,第一次查询时，加了 for update，上面一节说到，这种是加了排他锁，当前事务查询切换到当前读的模式下。第二张图是在事务 b 执行完 COMMIT 后的状态，可以看到程序出于 waiting 状态中，很明显就是被事务a阻塞了。等待事务 a 执行完成后，事务b才能执行完成。由于事务b被阻塞，所以在事务 a 未提交之前，只有事务 a 能操作 t_user 表中的数据，从而避免了幻读的情况发生。那么这个排他锁，具体是一个什么锁呢？

5. 总结

  1. 在MySQL中，MVCC能解决快照读模式下的幻读，不能解决当前读模式下的幻读。
  2. MySQL,采用间隙锁解决了当前读模式下的幻读。
