企业开发为何不用自增主键

Posted by jamie Blog on 2021-08-10 · 阅读 -- 次

1. 前言

在上大学的时候，我们有门课程，叫《数据库系统原理》，当时老师在讲数据库的基本使用的时候，建表的时候基本都是设置主键为自增。包括我们后面做课程实验，甚至与毕业设计。我们都这么干；不光我们这么干，教科书上的例子也是这么写的。以至于，我们后来毕业进入公司上班的时候，发现公司基本不这么做。这时候，我们就要思考了，为啥企业开发基本不用自增主键呢？

2. 自增主键有啥缺陷

企业开发不用自增主键，肯定存在他的一些弊端，我们在学校中，自己做一些项目的时候，用自增主键，也是完全没有问题。

但是公司的项目不能跟其相提并论。这里我们不妨来假设一下，公司项目数据库设计的时候吗，采用自增主键会存在什么问题？ 这里我们假设有这么一张订单表（ orders ），该表大约有一亿条数据，由于数据量大，我们要将其分表，现在暂其分为4张。

如下：

上面我们是均分，每个分片为 2500w 条数据。由于自增主键是在每个表结构自己维护的，经历了上面的分片后，四个表的最大主键 id 分别为：25000000，50000000，75000000，100000000；此时我们要插入一条数据，为了均分，我们一般采用 hash 计算，若计算出来的分片是第 0 个，那么插入的数据 id 为 25000001。

不知大家发现问题了没有， id 为25000001的数据已经为第二个分片中存在了。这样就导致了 id 不唯一。这样在后期的查询中也会存在某些不可预知的问题。 还有就是后期进行扩容，又得重新计算。所以上面所说的进行 hash 计算，获取分片节点的方法，在这种情况下不是很可取！

这个时候，有同学可能就要说了，那么我们在最初分片的时候，也通过 hash 计算进行选取分片，会不会存在以上问题呢？

答案是肯定的。由于我们 mysql 中，自增 id 是每个表独有的，不相关，所以肯定还是会存在上述问题。

若在上述情况下，我们进行新的数据插入，就只能在最后一个节点进行插入了，为了让每个节点均匀，就得还加一个节点。


此时所有的新数据都要对该分片访问，请求全部都打在了该分片上，这就是尾部热点效应。

综上所述：自增主键必须连续，且在数据分片的时候，只能采用 范围分片的方式，这样会产生尾部热点效应。

3. 是否可以用 UUID 做主键

那么是否可以用 UUID 做主键呢？

这里我们先给出答案：建议不要这么干。

UUID 是通过某种算法，计算出来的一个全世界唯一的字符串。这个可以保证全局 id 的唯一性，但是这个字符串并不是有序的，由于该特性，导致了我们将 UUID 作为主键的时候，会导致大量的索引重排（这里涉及到索引的具体数据结构），这里就不做赘述。

4. 建议用什么来做主键

那么我们在进行企业级项目开发的时候，用什么来作为主键 id 合适呢？关于这个问题，很多公司都有自己的相应主键 id 生成策略，也都有自己的一套实现。

这里推荐一种现成的算法实现：雪花算法（ Snowflake ）， 雪花算法是 Twitter 公司分布式项目采用的 Id 生成算法。

如下是雪花算法生成的 id 结构：

第一部分是1位的符号位，这个并没有实际的用处，主要是为了兼容长整型的格式。
第二部分是41位时间戳，用来记录本地的毫秒时间。
第三部分是机器id，这里说的机器就是生成id的节点，用10位长度给机器做编码，那就是最大规模可以达到1024个节点（2的10次方）。
第四部分是12为的序列号，序列的长度决定了一个节点1毫秒能生成的ID数量，12为就是4096（2的12次方）。

根据以上的生成规则，在我们企业开发中是绝对够使用的。

那么雪花算法有什么缺陷呢？ 本地时钟回拨的问题，由于生成的id是基于本地时间戳来生成的，若我们将本地时间进行调整，就有可能会出现id重复的情况。不过这种情况基本不会发生，可以忽略。

5. 总结

  1. 企业开发，用自增 id 在数据分片的时候，只能采用 范围分片的方式，会产生尾部热点效应。
  2. 不建议采用 UUID 作为主键。
  3. 建议采用雪花算法生成 id 作为主键，雪花算法在本地时钟回拨的情况下有可能会存在 id 重复问题。
