一次使用分布式锁无效的惨痛经历

Posted by jamie Blog on 2021-04-14 · 阅读 -- 次

1.背景

由于公司业务原因，我就不方便那当时的具体场景进行分析了，我这里就简单的列举一个示例，用来阐明当时碰到的问题。请原谅我词穷，可以说的例子并不是那么的恰当！

我这里就列举银排队办理业务的场景，我们在营业厅办理业务一般到银行都要进行排号，我们在门口的排号机器上选择具体办理的业务大项，如贷款办理，基础信息变更，业务咨询，存取款，办理储蓄卡。我这里就简单列举一下（仅仅为示例，不符合真实业务场景），那么每个业务大项都有相应的窗口进行办理，我们这里假设每个大项只有一个窗口办理，上面有 5 个大项，那么我们就假如有5个窗口，办理这 5 项业务，分别是贷款办理窗口，基础信息变更窗口，业务咨询窗口，存取款窗口，办理储蓄卡窗口。每个窗口办理业务都是独立运行的，互不干扰。下面我简单的画一张图。

现在就有一些客户来办理业务了，第一个来的是张三，来办理业务咨询的业务，那么就在取票机上拍了一个号，号码：yw_001，然后等业务咨询窗口叫号，当叫到 yw_001 的时候，就去窗口办理业务。后面李四也来了，也要办理一个业务咨询的业务，yw_002，没等到自己的号时，李四只能在一旁候着，等待时间为30分钟，若等待时间过了，上一个客户还没有办理完成，则在自己的排号上标记一个次数为1，后面每次来等待都标记的次数都要递增，假设等候排了三次还没有排到，那么就通知改客户，明天再来。我想要是银行真是这流程，客户肯定要被银行折磨死，哈哈哈。我们假设窗口不是自己叫号，是通过客户一直去询问的方式来实现的。（虽然现实中不可能这么干）。

2.实现与发现问题

为了实现上面的逻辑，我这边进行了设计，我写了一个线程池。 专门跑一个线程去让客户询问自己的业务窗口，下图有说明。

此时，遍历第一个 yw_001 ，线程直接叫该客户张三去业务窗口办理业务，然后继续遍历第二个客户 yw_002 ，有让该客户李四去业务窗口办理业务。但是同一个窗口只能串行办理业务，在此时 yw_002 的客户李四，就只能去等，我们可以设置一个等待时间，比如 30分钟，30分钟 时间后还不能办理自己的业务，就回到等候区。

    }

}

大概实现就是上面的代码。写完了，就迫不及待的跑起来测试一把，结果一跑起来，发现大量的获取锁超时，然后很直观的看见，等候区中的所有票次数都涨起来了，一会时间，只有业务窗口第一个客户办理成功了，其他客户的次数也很快达到了三次，看起来好像还是并行执行的。

3.推断原因与解决问题

根据上面现象，第一个直觉告诉我，是分布式锁没有锁住的问题，没锁住。

于是为了验证时锁的问题，我在 handleBusiness 上加上了 handleBusiness ，由于当前不是集群环境，完全可以这么搞。

public synchronized void handleBusiness(String no)

然后我再次运行，发现也没问题了。没有出现上面并行执行的情况。那么肯定是锁的问题了。

于是我查看日志，发现之前大量的锁超时情况，意思是等到了超时时间，还是没有获取到锁。（当然这里肯定不是设置的 30 分钟，不然那可真是难等呢）。

于是我再次梳理了一下代码，有一个线程一直遍历等候区的客户，然后交给其他线程去处理，那么若是同一个窗口出现了很多客户排队的情况，就算是第一个客户办理业务不到30分钟，就算是20分钟一个客户，那么第二个客户就等20分钟后才能获取到锁，然后第二个客户得到锁后，才开始办理业务，又执行了20分钟，此时第三个客户要等到 40 分钟，才能执行，但是此时就已经达到超时时间了。那么第五个，第六个，第七个 ….. ,也是同理，都已经是超时的情况。所以在第二个客户执行过程中，后面的客户都全部超时了。

那么肯定是我们代码上的逻辑漏洞，导致获取到锁失败的情况，也执行了后面的逻辑。所以可以定位到 lock.acquire(); 代码。

调试发现，这行代码有个返回值，就算获取锁超时也是返回的false。难怪，所以我这个地方应该判断一下，只有获取到锁成功的情况才执行。

public void handleBusiness(String no){
    try{
         String[] arr = no.sqlit(":");
        //等候次数大于三次，直接结束
        if(arr.lenth > 1 && Integer.parseInt(arr[1]) >= 3){
            return;
        }

        String business = no.sqlit("_")[0];
        //获取分布式锁，粒度为业务类型，相同业务类型只能串行执行 参数 30 表示没有获取到锁时等待 30 分钟 
      
        Lock lock = lockFactory.getLock(30, "bank_wait", business);
        //获取到锁
        if (!lock.acquire()) {
            return;
        }
        //设置等候次数+1
        .....
        //办理业务
        //.....
    } cache (Exception e){
        waitBlock.add(no)
    }

}

完美解决。

4.总结

上面的例子跟我们真实的业务有些出入，我们这边其实重试后还有个判断，每次等待的时候，会去计算设置下一次执行的时间，所以在handleBusiness中首要就是判断执行时间是否达到，没达到直接return。

针对这次的问题，还是由于对公司封装的分布式锁不太理解的原因，之前公司封装的，我们也没有用过，本次第一次。但是后面可就长心了，知道什么地方要注意什么。这次耗了不少时间。写下此篇以此谨记。
