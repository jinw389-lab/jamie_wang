循环依赖底层原理分析

Posted by jamie Blog on 2021-03-27 · 阅读 -- 次

1. 提出问题

对于会 java 的同学，对 Spring 不可能陌生吧， Spring目前为止，不管什么项目中，都存在他的影子， Spring 最核心的两大模块就是 IOC 与 AOP ，那么说到这些就不可能不提到依赖注入，既然都依赖注入了，各个 bean 之间不免会存在相互依赖的情况，那么循环依赖的情况也是避免不了的。但是我们在开发中，好像没有过多的去关注循环依赖的情况，是吧？这是因为，大多情况下循环依赖，Spring 帮我们解决了，所以我们可以说是没有感知。

那么问题来了，Spring 是怎么帮我们解决循环依赖的问题的呢？它的原理是什么？有哪些循环依赖他不能帮我们解决呢？

2. 什么是循环依赖

要搞清楚上面的问题，我们首先要明白什么是循环依赖？这个问题，我们举个例子最好说清楚。

那么不考虑 Spring，循环依赖的问题很常见。

A a = new A();
B b = new B();

a.b = b;
b.a = a;

通过上面的对象赋值后， A 和 B 就互相依赖了。 是吧。这段代码一看就明白了。

但是，这样也没问题啊。为什么在 Spring 中就是有问题呢 ？ 那是因为在 Spring 中对象不是通过 new 出来的，在Spring中，生成一个bean，都是要经过严格的生命周期。就是因为 bean 的生命周期，所以才会出现循环依赖的问题。

3. 简单说一下 bean 的生命周期

上面说到在 bean 的生命周期中会出现循环依赖的问题，那么 bean 的生命周期是如何的呢。

bean 的生命周期就是在 Spring 中， bean 是如何生成的。

  1. Spring 扫描 class 得到 BeanDefinition （BeanDefinition前面的文章有提到）
  2. 根据得到的 BeanDefinition 生成 bean
  3. 根据 class 推断构造方法
  4. 根据推断出来的构造方法，通过反射，生成对象
  5. 填充对象中的属性，通过依赖注入
  6. 如果对象中的某个方法存在 AOP，则要生成代理对象
  7. 把最终生成的代理对象放入单例池中。

bean 的生命周期不止上面的几步，比如Aware回调，初始化等等，这里就暂时省掉了。
可以看出，在 bean 的生成过程中，会存在实例化new的步骤，上面第四步，反射。然后在第五步中对实例对象的属性进行填充，这里是通过依赖注入的方式，那么依赖注入是如何做的呢？

就拿上面 A,B 相互依赖的例子来说。

首先实例化 A 对象，A对象就要经过他的生命周期，到第五步的时候，发现要依赖 B 对象，这个时候，通过属性名去单例池中去取对象 B 的实例，发现取不到，没有。那么这个时候咋办呢？
只能去实例化 B 对象啊，这个时候B对象就要经历他的生命周期，到第六步的时候，发现要依赖 A ，就去单例池中取对象，发现也没有，因为 A 对象还没有走完他的生命周期没有放入单例池。
有没有发现什么问题啦。这个时候拿到又去实例化A对象吗？发现也不对吧。这个时候就是发生了循环依赖的问题。这样最终的结果就是 A 和 B 对象都创建不出来。

假设一下 A 对象存在 AOP 代理呢，这样的话，我们在对 B 对象中的 a 属性进行赋值时，就不能简单的从 originalMaps 中获取对象呢，因为该 map 中的对象是原始对象，存在 AOP 的话，就必须赋值为代理对象，那么在什么时候生成代理对象呢？我们可以在第十一步从 originalMaps 中获取对象的时候，判断改对象是否要被代理。若是，则生成代理对象赋值给 a 变量。

好吧，现在没问题了。

bean 生命周期继续执行，A 的生命周期执行到第六步，发现要生成 A 的代理对象，这样又出现问题了。尴尬！所以我们再第六步的时候，还要去进行判断，若已经生成过了代理对象就不用生成了。继续执行完成，将对象都放入单例池中。

好吧，我们从头看看。我们从头到尾用到了两个 map ，originalMaps存储原始对象，earlySingleObjMaps存储的是代理对象，然后在加上单例池共三个容器。对照这 Spring 来看正好是他的三级缓存。

一级缓存： 单例池 —-> singletonObjects
二级缓存： earlySingleObjMaps —-> earlySingleObjects
三级缓存： originalMaps —-> singletonFactories

这里值得注意的是，singletonFactories 与 originalMaps 还是不同的，在 Spring 中 singletonFactories 缓存的是 ObjectFactory, 表示对象工厂，用来创建某个对象。

5. Spring 中是否彻底解决了循环依赖

我们上面列举到的例子，Spring 通过三级缓存解决了循环依赖的问题，那么什么情况下的循环依赖问题不能解决呢？

在 Spring 生命周期最后， Spiring 提供了 BeanPostProcessor 可以去对 Bean 进行加工，这个加工不仅仅知识能修改 Bean 的属性值，也可以替换掉当前的 Bean。而 BeanPostProcessor 的执行是在 Bean 的生命周期中是处于属性注入之后的，循环依赖是发生在属性注入的过程中，所以很有可能导致， 注入给 B 对象和经历过完整生命周期之后的 A 对象，不是同一个对象。这个问题，就不对了。

所以在这种情况下的循环依赖，Spring 是解决不了的。因为在属性注入的时候，Spring 也不知道 A 对象后续会经过哪些 BeanPostProcessor 以及会对 A 对象做什么处理。

上面说的这种情况，基本很少发生，我们在实际的开发中，也基本不会这样去做。

6. 总结

1，Spring 通过三级缓存解决了循环依赖。
2，BeanPostProcessor 后置处理器，若替换当前 Bean 的情况下，Spring 解决不了这种情况，因为 Spring 只能解决属性注入过程中的循环依赖问题。
