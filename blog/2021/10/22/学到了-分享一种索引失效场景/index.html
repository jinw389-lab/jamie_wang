Posted by jamie Blog on 2021-10-22 · 阅读 -- 次

1. 前言

嘻嘻！有一段时间没有更新了，一方面是由于这段时间工作生活的确比较忙，事情比较多；二方面是自己知识的确匮乏，没有找到适合写的东西。不过，今天有一点空，工作上的本次迭代，我昨天提前干了，今天就可以抽出点时间。

我们都知道，在使用 MySql 的时候，就算我们建了索引，实际在查询的过程中，也不一定能走索引。那么在什么情况下会导致索引失效呢？我想大部分朋友都能说上的几点。有一些我们比较常见的，这也算我们面试的时候，经常被问到的问题。我下面就简单整理几个常见的情况。

结果是前两条索引生效，后两条中，只有最后一条生效。那么是什么原因导致索引失效呢？看看我们的建表语句。 t_utf8表的字符集编码为为utf8，t_utfmb4的编码为utf8mb4。两个表的字符集编码不同。

下面在来看看具体的执行计划 第四个执行计划是先查询的b表后查询的a表，与第三条执行计划正好相反。

第三条执行计划中 先执行select * from t_utf8m a where a.name = 'zz'; 再执行select * from t_utf8 b where b.name = 'a表的结果';

第四条执行计划中 先执行select * from t_utf8 b where b.name = 'zz'; 再执行select * from t_utf8m a where a.name = 'b表的结果';

普及个知识：

  1. 两表的字符集编码不同，在查询中会涉及到编码转换。
  2. 编码转换时，只能是utf8向utf8mb4转换。

所以在执行时三个执行计划就变成了
select * from t_utf8 b where CONVERT(b.name USING utf8mb4) = 'a表的结果';

第四个执行计划
select * from t_utf8m a where a.name = CONVERT('b表过滤出来的值' USING utf8mb4);

可以看到索引失效的根本原因还是由于在索引字段上存在函数操作。

那么为什么前两个执行计划为啥没有问题呢？那是由于int在两种类型下都是一致的，无效转换。

4. 总结

上面由于编码不一致导致索引失效的情况，当时在线上存在，但是我们在qa上复现的时候，发现没有问题。是由于，我们qa上的表编码都是utf8mb4,而线上是utf8和utf8mb4。导致在量表关联查询的时候，索引失效。

我们数据库中的表编码格式应该做到尽量统一。不建议同一个库存在不同的字符集编码。只要做到这一点，我们可以避免好些没必要的问题。
