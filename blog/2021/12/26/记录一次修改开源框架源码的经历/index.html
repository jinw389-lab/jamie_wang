记录一次修改开源框架源码的经历

Posted by jamie Blog on 2021-12-26 · 阅读 -- 次

1. 背景

由于项目上的需要。我们需要对我们之前引入的一个开源项目 json-schema 进行代码的修改。

1.1 json-schema 是什么？

现在我们来假设这么一个场景。我们写了一个接口，调用接口提交数据给服务端。我们服务端是不是要对接口传入的数据进行校验呢？

这个简单。不就是if判断一下吗？ 这都是很多小伙伴信手拈来的事。

这没错，这是我们惯用的手法，更如一些好点的办法就是引入Hibernate-Validator。这些都是我们只晓的方案。

那么问题来了。以上方案都是基于我们针对参数由我们自己的类定义。或者接口就是针对某一个具体的参数类型服务的情况。那么还有其他情况吗？

假如我想通过某一个json定义描述呢？ 如：

    "name" : {
        "type" : "boolean", 
        "required" : true

上面json用来描述参数字段 name 类型为 boolean ，且为必传。

这样的话，若我们有这么一个工具能够解析这个json定义然后对入参进行校验，那我们就没有必要去定义那么多非必要的类对象了 ， json-schema就是这样的一个工具。

其实json-schema还有一个非常强大的功能，就是可以根据根据json定义生成动态表单页面。那么有了这玩意儿，用户就可以根据自己的需求配置更加灵活的页面。

是不是感觉很牛逼。是不是特香。

有幸的是，这上面的两种特性，我们项目上都有实际运用。那么是什么原因导致我需要去修改其源码呢？

2. 为啥我们需要修改源码

一句话就是满足不了我们需求。 经过上面的介绍，我们大致明白了json-schema的作用。

我们修改其源码主要是第二个功能上得不到很好的满足。

上图流程显示了json定义的应用流程。最后一步也是我们想要看到的结果。由于项目特殊性，我们项目中定义了大量的类，通过类来生产json定义。恰好，这也是json-schema所支持的

可以看到上图编写类的字段定义顺序与生成json中字段的顺序不一致。感觉json-schema中是按照自然排序生成的。看到此现象，第一感觉就是@Attributes注解是不是有指定顺序的属性配置呢？我去查看源码，发现还真没有？


为了达到与类中字段的定义顺序一致的情况，可以有如下方案： 1，生产json后，对其顺序进行重排，这个涉及到json解析 2，需改框架排序源码，要阅读其源码。

方案二，写的代码应该是最少的，只是需要花点时间阅读源码。
方案一，还要根据json进行回溯类定义，最后修改json。

最后根据实际情况，我选择了方案2。

5. 总结

根据这次经历，我深刻认识到阅读源码，必须要有明确的目标，不能盲目的进行阅读。盲目读源码是没有多是意义的。
