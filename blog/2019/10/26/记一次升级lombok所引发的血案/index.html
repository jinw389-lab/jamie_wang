记一次升级lombok所引发的血案

Posted by jamie Blog on 2019-10-26 · 阅读 -- 次

1.案发背景

昨日，线上收到熔断报警，查看到报警日志。

可以得出，实例化DTO对象的时候，没有找到对应的构造函数。

2.解决问题

定位到报错的代码。

通过jackson将json反序列化成DTO对象。
通过查看最近的git日志，最近修改了lombok的版本以前是1.14.8，改成了1.18.8版本那么将版本还原回去，然后调试，问题也得到了解决。

3.排查原因

我们仅仅是升级了lombok的版本罢了，那么为啥会反序列化失败呢。我就开始了查找原因。 类中用了lombok，生成set和get方法和构造函数

①.反编译两个版本的DTO class。

我分别切换两个新老版本，生成DTO的class，然后进行反编译。

对比了一下，发现连个版本老版本在全局构造函数上面多了ConstructorProperties注解。这个注解平时没啥用到，没怎么关注，查看官网

https://www.cs.auckland.ac.nz/references/java/java6/api/java/beans/ConstructorProperties.html

了解到，该注解作用于构造函数，表明构造函数的参数如何与构造对象的getter方法相对应。那么剩下的应该是由于jack反序列化json生成对象的时候依赖了这个注解。然而新版本是没有这个注解的，就会报错。
我尝试添加无参构造函数，新老版本可以反序列化成功。
后面我尝试了使用gson进行json的反序列化，发现不管新老版本都是可以成功的。 说明不同的json处理工具实现的差异性。

    public Object deserialize(JsonParser p, DeserializationContext ctxt) throws IOException {
        if (p.isExpectedStartObjectToken()) {
            //判断是的存在无参构造函数
            if (this._vanillaProcessing) {
                return this.vanillaDeserialize(p, ctxt, p.nextToken());
            } else {
                p.nextToken();
                return this._objectIdReader != null ? this.deserializeWithObjectId(p, ctxt) : this.deserializeFromObject(p, ctxt);
            }
        } else {
            return this._deserializeOther(p, ctxt, p.getCurrentToken());
        }
    }

4.总结

  1. 开发过程中，不要随意修改一些工具包的版本，就算要升级，也要事先了解不同版本的差异，做好必要评估。
  2. 编码中，进来写好单元测试，把问题尽早暴露出来。若此次问题，有好的单元测试，那么这个问题，打包的时候就已经可以暴露出来了，就不会在线上引发，导致情节严重。
  3. 工具类之间的搭配使用也要注意，有很多工具类都可以实现同一功能，帮我们解决问题。但是底层实现可能差异很大，一不下心可能就会出错。
  4. 由于手动添加了有参构造函数，就没有了无参构造函数，要手动补上。在编码时，没有特定的需要，一个类都要有无参构造函数。
