我在项目中运用到的数据源与选型

Posted by jamie Blog on 2022-05-10 · 阅读 -- 次

1. 前言

在项目开发过程中，我所用到的数据库基本如下：MySQL , MongoDB , Elasticsearch , Redis , PostgreSQL。其中关系型数据库就 MySQL 和 PostgreSQL,可以归结为异类，MongoDB , Elasticsearch 是非结构的NoSQL文档型数据库，Redis 是一种非结构化的，高性能的NoSQL数据库。所以按照类型划分，见下面表格。

数据库 类型
MySQL 关系型
PostgreSQL 关系型
MongoDB 文档型
Elasticsearch 文档型
Redis NoSQL

2. 在工作中的选型

2.1 关系型数据库

在开发一个项目，主要是业务系统，关系型数据库感觉基本上是必不可少的。目前市面上关系型数据库也是非常多，五花八门。但是在做java的基本都是将MySQL作为首先，其中有一部分是在中国it氛围的原因，说白了就是随大流。另一方面是由于运维开发相对简单，碰到问题，网上文章也很丰富，很容易找到解决方案。现在出去找工作，只要你是做java服务端开发的，感觉MySQL技术栈那就是必不可少。

那么MySQL在国内已经默认为关系型数据的首要选择了，我们为啥还选择了 PostgreSQL 呢? 下面我们来做一个简单的对比。对比完了才会知道他们各自的优劣，根据每个公司的一些具体情况作出合理的抉择。

2.1.1. PostgreSQL相对于MySQL的优势

1、在SQL的标准实现上要比MySQL完善，而且功能实现比较严谨；

2、存储过程的功能支持要比MySQL好，具备本地缓存执行计划的能力；

3、对表连接支持较完整，优化器的功能较完整，支持的索引类型很多，复杂查询能力较强；

4、PostgreSQL主表采用堆表存放，MySQL采用索引组织表，能够支持比MySQL更大的数据量。

5、PostgreSQL的主备复制属于物理复制，相对于MySQL基于binlog的逻辑复制，数据的一致性更加可靠，复制性能更高，对主机性能的影响也更小。

6、MySQL的存储引擎插件化机制，存在锁机制复杂影响并发的问题，而PostgreSQL不存在。

2.1.2. MySQL相对于PostgreSQL的优势：

1、innodb的基于回滚段实现的MVCC机制，相对PostgreSQL新老数据一起存放的基于XID的MVCC机制，是占优的。因此MySQL的速度是高于PostgreSQL的；

2、MySQL采用索引组织表，这种存储方式非常适合基于主键匹配的查询、删改操作，但是对表结构设计存在约束；

3、MySQL的优化器较简单，系统表、运算符、数据类型的实现都很精简，非常适合简单的查询操作；

4、MySQL分区表的实现要优于PostgreSQL的基于继承表的分区实现，主要体现在分区个数达到上千上万后的处理性能差异较大。

小结：虽然两数据库在关系型数据库的标准上都有支持，但是在不同功能实现上的区别和实现力度都不太相同。在某些特定的情况下，也存在利弊。

主要整理了上面的几点。而我们之前采用PostgreSQL就在于我们项目里面会用到一些很特定的SQL函数，来支持业务的查询或操作，若使用MySQL的话，实现起来就相对要负责得多，其他方面其实在业务上来说，两数据库都没有特别的影响。所以最后采用了 PostgreSQL 。

2.2 文档型数据库

这里主要讨论一下MongoDB和Elasticsearch。虽然这两种数据库都是文档型数据库。但是区别确实非常大的。

指标 MongoDB Elasticsearch
编写语言 c++ java
客户端操作方式 专门的驱动driver RESTFul接口
操作语句 专门的复杂语句，学习成本高 专门的复杂语句，学习成本高
分片方式 hash和range hash
分布式 由“前置查询路由+配置服务+shard集合”，需要手动配置集群服务 天然分布式
内部存储方式   到排索引+docvalues+fielddata
索引 手动建立索引 所有字段自动建立索引
全文检索 全文检索字段个数有限制 强大的分析器且可以灵活组合，查询时智能匹配
数据安全性 理论上，没有数据丢失 非实时，存在数据丢失风险
大数据查询性能上 很高 非常高

以上是我这边整理的一些关键信息的对比。基于我们公司业务的需求，由于公司业务发展，有很多数据存在指数型递增，我们采用MongoDB+分表的方式进行存储，并且这些数据是安全性要求高，所以在排除了MySQL的前提下，首选的就是MongoDB。

报表统计相关，采用的是Elasticsearch。这一点也是基于Elasticsearch的全文检索性能上的考虑，但是Elasticsearch在聚合上面的性能貌似并不是特别高，所以我们在Elasticsearch中存储的是初步聚合统计的数据，然后业务上根据具体情况在做二次聚合查询。这样在比较复杂的查询情况下，也能保证查询性能非常高。

2.3 Redis

感觉这块基本没啥可说的呢，在Redis适用领域，基本上算是标杆了,前几年可能还会提到memercache,也是由于他不支持复杂的数据结构，外加不支持持久化，被Redis打压得没有一席之地。

我们项目上Redis主要用于缓存来增加查询性能，登陆用户的基本信息与权限，分布式锁，还有自研多任务队列组件，这个在之前文章中有提到。

3. 总结

本篇文章是这几年工作以来，对于使用到的数据库的一个全面汇总，并分类进行对比。以及项目上如何根据具体情况来选型。
