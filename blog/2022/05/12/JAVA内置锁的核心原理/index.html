JAVA内置锁的核心原理

2. 对象结构

2.1 对象的三大部分

先来聊聊对象的结构。包括三部分：对象头、对象体和对齐字节。

（1）对象头
对象头包括三个字段，第一个字段叫作Mark Word（标记字），用于存储自身运行时的数据，例如GC标志位、哈希码、锁状态等信息。第二个字段叫作Class Pointer（类对象指针），用于存放方法区Class对象的地址，虚拟机通过这个指针来确定这个对象是哪个类的实例。 第三个字段叫作Array Length（数组长度）。如果对象是一个Java数组，那么此字段必须有，用于记录数组长度的数据；如果对象不是一个Java数组，那么此字段不存在，所以这是一个可选字段。
（2）对象体
对象体包含对象的实例变量（成员变量），用于成员属性值，包括父类的成员属性值。这部分内存按4字节对齐。
（3）对齐字节
对齐字节也叫作填充对齐，其作用是用来保证Java对象所占内存字节数为8的倍数HotSpot VM的内存管理要求对象起始地址必须是8字节的整数倍。对象头本身是8的倍数，当对象的实例变量数据不是8的倍数时，便需要填充数据来保证8字节的对齐。该部分不是必须的，没有特殊含义。

2.2 简要说明一下对象头中的三个字段

（1）Mark Word（标记字）字段主要用来表示对象的线程锁状态，另外还可以用来配合GC存放该对象的hashCode。 这一块在下面谈到锁的实现部分会重点聊。
（2）Class Pointer（类对象指针）字段是一个指向方法区中Class信息的指针，意味着该对象可随时知道自己是哪个Class的实例。
（3）Array Length（数组长度）字段占用32位（在32位JVM中）字节，这是可选的，只有当本对象是一个数组对象时才会有这个部分。

2.3 Mark Word结构信息

前面有提到，Mark Word字段是用来表示线程锁的状态的，里面包含了锁的信息，在java内置锁中，锁的状态分别无锁，偏向锁，轻量级锁，重量级锁。在java 1.6之前。java内置锁只有一个重量级锁，在1.6之后，针对synchronized关键字做了优化，此后才有了这四个状态。并且这四个状态也会随着线程竞争激烈递增而升级，而且不是一个可逆的过程。所以锁的只有升级过程，没有降级过程。

2.4 不同状态下，Mark Word的结构数据变化

在32位下的结构信息
在64位下的结构信息

下面针对64位来做详细描述：

（1）lock：锁状态标记位，占两个二进制位，由于希望用尽可能少的二进制位表示尽可能多的信息，因此设置了lock标记。该标记的值不同，整个Mark Word表示的含义就不同。
（2）biased_lock：对象是否启用偏向锁标记，只占1个二进制位。为1时表示对象启用偏向锁，为0时表示对象没有偏向锁。
（3）age：4位的Java对象分代年龄。在GC中，对象在Survivor区复制一次，年龄就增加1。当对象达到设定的阈值时，将会晋升到老年代。默认情况下，并行GC的年龄阈值为15，并发GC的年龄阈值为6。由于age只有4位，因此最大值为15，这就是-XX:MaxTenuringThreshold选项最大值为15的原因。
（4）identity_hashcode：31位的对象标识HashCode（哈希码）采用延迟加载技术，当调用Object.hashCode()方法或者System.identityHashCode()方法计算对象的HashCode后，其结果将被写到该对象头中。当对象被锁定时，该值会移动到Monitor（监视器）中。
（5）thread：54位的线程ID值为持有偏向锁的线程ID。
（6）epoch：偏向时间戳。
（7）ptr_to_lock_record：占62位，在轻量级锁的状态下指向栈帧中锁记录的指针。
（8）ptr_to_heavyweight_monitor：占62位，在重量级锁的状态下指向对象监视器的指针

3. 偏向锁原理

在大多数情况下，同一段同步代码块，基本很少出现锁竞争的情况，为了降低CPU从用户态切换为内核态的频率，减少CPU资源的浪费，就引入了偏向锁。

偏向锁的原理就是，在一个线程进入代码临界区的时候，若没有存在竞争，则会进入偏向状态，此时，锁标志位(lock)变为01,偏向标志位（biased_lock）改为1，最后采用CAS操作将线程id写入Mark word 中。此后，该线程若重入，直接可以判断Mark word中的记录的线程id是否是自己，是的话，直接进入同步代码块，都无需进行CAS操作，性能极高。从而有效提升程序的性能。若其他线程尝试获取锁，发现Mark work中的线程id并不是自己的线程id，此时偏向锁结束，撤销，升级为轻量级锁。

偏向锁主要应用于不会存在线程竞争的情况，这样可以有效提高程序性能。 在存在有多个线程竞争的情况下，偏向锁会发生频繁的偏向锁撤销情况，这样会有较大的性能开销。

注： （1）在偏向锁的前提下，若该线程执行完成后，偏向锁依然不会撤销，对象头中的Mark word依然保留了该线程的id，锁标志位依然是偏向锁状态。
（2）偏向锁的功能不是一启动程序就生效的，存在一定时间的延迟，JVM默认这个延迟时间是4s。为什么要延迟呢？是由于在程序启动中，有很多加载资源的操作，并且这些操作与偏向锁没有任何关系，一开始就给对象加上偏向锁是没有意义的，而且还会消耗一定的性能，不启用，可以很大程度上减少偏向锁撤销带来的性能影响，所以偏向锁被设计为延迟生效。

3.1. 偏向锁撤销

偏向锁的膨胀只有在多个线程竞争才会出现，那么偏向锁的撤销是在何时触发呢？ 基本有两种情况会触发撤销操作：

  1. 第二个个线程发生竞争，发现mark word中的线程id不是当前线程的id时，触发撤销。
  2. 锁对象，发生hashcode计算。因为hashcode计算后的值，是要保存到mark word中的，这个时候也是要撤销。

下面是锁撤销过程：

（1）在一个安全点停止拥有锁的线程。
（2）遍历线程的栈帧，检查是否存在锁记录。如果存在锁记录，就需要清空锁记录，使其变成无锁状态，并修复锁记录指向的Mark Word，清除其线程ID。
（3）将当前锁升级成轻量级锁。
（4）唤醒当前线程。

3.2. 偏向锁膨胀

前面已经提到，存在多个线程竞争的时候，首先是要对锁对象中的mark word中的线程id进行判断，若id不是当前线程的id，JVM则会判断mark word中的线程id的线程是否存活，若已经不存活了，则撤销到无锁状态，然后重新偏向。若还存活，则进一步判断线程的锁记录是否持有偏向锁，若持有，则直接将其撤销，然后升级为轻量级锁。

4. 轻量级锁原理

在大多数情况下，线程竞争到锁，很快就会执行完，然后就释放掉锁，其他线程然后再来争抢锁。若这个时候采用重量级锁，CPU就会频繁的用户态与内核态进行切换。所以基于这个因素的考虑，JAVA在此引入了轻量级锁来进行优化。轻量级锁是采用CAS自旋来锁来实现，在线程没有获取到锁的情况下，线程会进行自旋，这样不会导致CPU用户态转为内核态的切换，自旋几次后就会有很大概率获取到锁。以此提高了程序性能。

轻量级锁的实现过程： 在线程即将进入代码临界区的时候，去获取锁的一个争抢，若此时，内置锁没有被锁定，JVM首先会在线程的方法栈帧中建立一个锁记录空间，用来存储锁对象的Mark word拷贝。然后线程开始执行CAS操作，将锁对象的Mark word的ptr_to_lock_record尝试更新为该线程的锁记录空间地址。若这个操作成功了，就代表该线程获取到了锁。接着JVM会将lock锁记录改为00（轻量级锁）。随后JVM也会将Mark word中原来的锁对象信息拷贝到保存到锁记录中Displaced Mark Word中，最后将锁记录中的owner指针指向锁对象。下面画一个简图。

4.1 轻量级锁分类

普通自旋锁： 在线程没有争抢到锁时，开始自旋尝试获取，直到获取到锁为止（占有锁的线程释放）。由于自旋会消耗一定的CPU，相当于这个线程，什么也不做，就在本地循环，存在一定的资源浪费。这也是为什么轻量级锁适用于占有锁时间很短的情况。这样的话，锁就能很快释放，自旋的线程要不了几次自旋就能获取到锁。这里存在着这么一个权衡。在java中，默认自旋有次数限制，默认值为10次。

自适应自旋锁： 自适应自旋锁是相对普通自旋锁来说的，普通自旋锁自旋次数是固定的，自适应就不是固定的次数，可以根据自身情况动态调整。实现的原理就是根据上一次在同一个锁上的自旋时间来判断；若前一次同一个锁对象上成功获取到过锁，那么JVM认为本次也是有很大概率能够获取到锁的，此时就可能自旋的次数会多一点，时间也相对要长一些。若对于这个锁，抢占的线程很少获取成功，那么自适应自旋锁就会根据实际情况，减少自旋次数与时间，必要情况下可能还会取消自旋，直接放弃锁的一个争抢。

在java 1.6是普通自旋锁，1.7后默认是开启了自适应自旋锁。

自旋锁也被称为轻量级锁，乐观锁，这个过程没有将线程进行挂起，线程会持有CPU的执行权，线程会不停的空轮询。

4.2 轻量级锁的膨胀

轻量级锁适用于占有锁时间很短的情况。但是在实际场景下，还是会存在很多占有锁时间很长的情况，那么针对这种情况，轻量级锁反而是不太适用的。当碰到这样的情况，轻量级锁就会发生锁膨胀，转变为重量级锁。

5. 重量级锁原理

在java中，每个对象创建成功后，都会跟随着创建一个监视器。这个监视器的生命周期与对象相同。对象销毁的同时，与之对应的监视器也会同步销毁。监视器可以理解为一个同步机制。相当于一个用来监视这些线程进入的特殊房间，其义务是保证（同一时间）只有一个线程可以访问被保护的临界区代码块。

线程流转过程如下：

cxq：
竞争队列，所有要竞争锁的线程都会先进入此队列。
线程争抢锁之前都会对cxq队头元素进行CAS争抢，所以该处不是公平的，正因为如此，java中的重量级锁是非公平锁。获取线程是从队尾获取的，并且只有owner线程操作。

EntryList：
cxq中具有资格成为候选资源的线程就会移动至EntryList中。
cxq和EntryList逻辑上都属于等待队列，为了降低线程对cxq的并发访问，建立了EntryList队列。在owner线程释放锁时，JVM会从cxq的队尾迁移一个线程到EntryList中，并且制定EntryList中的某一个线程为OnDeck线程（一般是head线程）。

WaitSet：
获取到锁的线程，调用了wait方法后将被移动到WaitSet中。某个线程调用了notify或者notifyAll唤醒该线程，该线程才会移动到EntryList中。

处于ContentionList、EntryList、WaitSet中的线程都处于阻塞状态，线程的阻塞或者唤醒都需要操作系统来帮忙，Linux内核下采用pthread_mutex_lock系统调用实现，进程需要从用户态切换到内核 态。这也是重量级锁非常消耗性能的原因。

6. 偏向,轻量级,重量级锁比较

总结一下synchronized的执行过程，大致如下：
（1）线程抢锁时，JVM首先检测内置锁对象Mark Word中的biased_lock（偏向锁标识）是否设置成1，lock（锁标志位）是否为01，如果都满足，确认内置锁对象为可偏向状态。
（2）在内置锁对象确认为可偏向状态之后，JVM检查Mark Word中的线程ID是否为抢锁线程ID，如果是，就表示抢锁线程处于偏向锁状态，抢锁线程快速获得锁，开始执行临界区代码。
（3）如果Mark Word中的线程ID并未指向抢锁线程，就通过CAS操作竞争锁。如果竞争成功，就将Mark Word中的线程ID设置为抢锁线程，偏向标志位设置为1，锁标志位设置为01，然后执行临界区代码，此时内置锁对象处于偏向锁状态。
（4）如果CAS操作竞争失败，就说明发生了竞争，撤销偏向锁，进而升级为轻量级锁。
（5）JVM使用CAS将锁对象的Mark Word替换为抢锁线程的锁记录指针，如果成功，抢锁线程就获得锁。如果替换失败，就表示其他线程竞争锁，JVM尝试使用CAS自旋替换抢锁线程的锁记录指针，如果自旋成功（抢锁成功），那么锁对象依然处于轻量级锁状态。
（6）如果JVM的CAS替换锁记录指针自旋失败，轻量级锁就膨胀为重量级锁，后面等待锁的线程也要进入阻塞状态。总体来说，偏向锁是在没有发生锁争用的情况下使用的；一旦有了第二个线程争用锁，偏向锁就会升级为轻量级锁；如果锁争用很激烈，轻量级锁的CAS自旋到达阈值后，轻量级锁就会升级为重量级锁。
