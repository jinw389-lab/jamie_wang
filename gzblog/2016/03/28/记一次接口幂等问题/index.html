记一次接口幂等问题

Posted by jamie Blog on 2016-03-28 · 阅读 -- 次

1,问题描述

  假如有一个抽奖系统，一期抽奖只能抽奖一次，开发时未考虑到幂等性问题，导致线上出现重复开奖问题。

2,修复前逻辑

  1. 根据抽奖期数id获取本次抽奖详情
  2. 获取本次抽奖期数时间区间
  3. 获取本次抽奖期数各奖项配置（例如：一等奖3位，二等奖8位，三等奖20位）
  4. 查询列表，筛选中奖
  5. 更新本次抽奖状态为已开奖

当时现场暴露的问题是，操作员点击一次开奖按钮，根据后端日志排查发现后端收到了两次相同的请求，这可能是当时网络的问题，根据上面的逻辑，抽出来的中奖数恰是本次抽奖期数的配置中奖数量的两倍。

3,解决后逻辑

修改了两个地方
①. 查询出本次抽奖详情后先判断本次抽奖是否是未抽奖，若是则更新本次抽奖的状态为抽奖中，否则直接返回不做处理
②. 以上实现代码中需要加入到synchronized同步代码块中
完美解决，也许还有更好的解决方案，这里不谈，根据具体的业务要求，税务部门大多在一个与月只进行一次抽奖，也就是说这个方法一个月只执行一次，我们加入同步代码块虽然效率也没啥影响。起初开发时，由于经验不足，的确没有考虑幂等问题，写下这份博客，忘往后谨记！

4,谈谈对幂等的看法与理解

随便上网找度娘，基本都差不多，大体是这样说：就是一个操作无论执行一次还是多次所返回的结果是一致的，有些博客还列举数据库的select来说明，select是先天幂等的。

这里假设一种情况，服务a一直在insert数据库，表中的数据一直在增加，服务b则执行select操作，很显然，这里的结果就不同了，很有疑问啊。所以总结一下，幂等不是看返回结果是否一致，应该看得是对服务的影响。执行多次的select并不会对表数据造成影响，所以select是天然幂等的，这才是合理的解释。

下面看看update语句，分两种情况

update t_table set state = 1 where id = 1;
update t_table set state = state + 1 where id = 1;

第一句是幂等，第二句则不是幂等的;
根据结论insert不是幂等的，而delete是幂等的。
